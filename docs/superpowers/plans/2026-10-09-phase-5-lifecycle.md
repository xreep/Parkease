# Phase 5 — Booking Lifecycle, Cancellations, Notifications, Reminders

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Bookings move through ACTIVE/COMPLETED automatically; drivers can cancel with an exact policy-based refund preview; owners can cancel confirmed bookings (full refund); every user gets in-app notifications (bell, dropdown, page) alongside emails; drivers get a start reminder and owners an approval nudge.

**Architecture:** New `notification` package with a `Notifier` facade (email + notification in one call) that replaces direct email sends; `RefundService` generalised to partial amounts; `cancellation` logic in `booking` (`CancellationPolicyCalculator`, `CancellationService`); `BookingJobs` gains lifecycle and reminder jobs. Frontend adds a notification bell + page and cancel flows.

**Tech Stack:** Spring Boot 4.1.1 / Java 21 / PostgreSQL 16; React 19 + TS + Tailwind 4; TanStack Query; Vitest.

**Spec:** `docs/superpowers/specs/2026-10-04-smart-parking-design.md` — §6.5, §6.6, §19 and **§20 Phase 5 Decisions** (binding).

**Plan format:** contracts, exact rules/tables and required tests (complete code only where it removes ambiguity). Binding.

### Task 2: Partial refunds, cancellation policy and cancel endpoints

**Files:** `payment/RefundService` (generalise), `booking/CancellationPolicyCalculator`, `CancellationService`, endpoints in `BookingController` + `OwnerBookingController`, `dto/CancellationPreview`, `dto/CancelRequest`; `email/EmailTemplates` (+ cancellation templates); tests `booking/CancellationPolicyCalculatorTest`, `booking/CancellationFlowTest`, `payment/PartialRefundTest`.

- [ ] **Contract:**
  - `RefundService.refund(Booking b, Payment p, BigDecimal amount, BookingActor actor, String reason, RefundNotice notice)` (MANDATORY tx, locks held): `0 < amount ≤ remaining` where remaining = payment.amount − Σ non-FAILED refunds (else `IllegalArgumentException`); issues a provider refund for `amount`; recomputes payment status (`REFUNDED` when covered, `PARTIALLY_REFUNDED` otherwise, `CAPTURED` when 0) and `booking.refundAmount` via the existing recompute logic; records a timeline note; notifies via `Notifier`. `refundFull(...)` delegates to it. Retry/adoption/webhook paths keep working for partial amounts (adoption amount check compares that row's amount).
  - Earnings: after a refund, `net = base − refundedBase` where `refundedBase = min(base, refund total)` for driver cancellations (fees aren't refunded so the whole refund comes from base); `commission` unchanged; status `REVERSED` when `net == 0`, otherwise unchanged. Full-total refunds (owner/system/approval-pending cancellations) → `REVERSED`.
  - `CancellationPolicyCalculator.preview(CancellationPolicy policy, Instant start, Instant now, BigDecimal base)` → `(percent, refundAmount = base × percent / 100 HALF_UP, hoursBeforeStart)`. Thresholds use exact minutes: FLEXIBLE `≥60` → 100 else 50; MODERATE `≥1440` → 100, `≥120` → 50, else 0; STRICT `≥2880` → 50 else 0.
  - `GET /api/v1/bookings/{id}/cancellation-preview` (driver, own) → `CancellationPreview`:
    - `PENDING_PAYMENT` → cancellable, percent 100, refundAmount 0.00 (nothing paid), nonRefundable 0.00;
    - `AWAITING_APPROVAL` → cancellable, percent 100, refundAmount = total;
    - `CONFIRMED` with start > now → policy result on base; nonRefundableAmount = total − refundAmount;
    - otherwise `cancellable:false` with `reason` "Bookings can't be cancelled once they've started" / "This booking is already <status label>".
  - `POST /api/v1/bookings/{id}/cancel` body `{reason?: string ≤300}` → `BookingDetailDto`; under locks re-check; not cancellable → 409 `NOT_CANCELLABLE`. Effects: status `CANCELLED`, `cancelledBy DRIVER`, `cancelReason`; PENDING_PAYMENT → payment CREATED→FAILED "Cancelled by driver", no refund; AWAITING_APPROVAL → full refund of total, earning REVERSED; CONFIRMED → policy refund on base (skip provider call when 0), earning adjusted. Notifications: driver `BOOKING_CANCELLED` ("Booking cancelled" + refund line), owner `OWNER_BOOKING_CANCELLED`. Emails: driver "Booking cancelled – ParkEase" (refund amount or "No refund applies under the <policy> policy"), owner "Booking cancelled by driver – ParkEase".
  - `POST /api/v1/owner/bookings/{id}/cancel` body `{reason}` (required, ≤300) → only `CONFIRMED` with start > now else 409 `NOT_CANCELLABLE`; status `CANCELLED`, `cancelledBy OWNER`; full refund of total; earning REVERSED; driver notified/emailed "Your booking was cancelled by the owner – ParkEase" with reason + refund.
- [ ] **Tests:** calculator boundary table (59/60 min flexible; 1439/1440 and 119/120 moderate; 2879/2880 strict; rounding of odd bases e.g. base 33.33 × 50% = 16.67); flows: driver cancels PENDING_PAYMENT (no refund, slot freed for another reserve), AWAITING_APPROVAL (full total refunded), CONFIRMED moderate >24 h (base refunded, fees kept, payment PARTIALLY_REFUNDED, earning net 0 → REVERSED), CONFIRMED moderate 3 h (50% base, earning net = 50% base, still HELD), strict 10 h (0 → no provider call, still CANCELLED); ACTIVE → 409; owner cancel CONFIRMED → full total refund, payment REFUNDED; other owner → 404; partial-refund then webhook `refund.processed` keeps `PARTIALLY_REFUNDED`; preview values match the subsequent cancel.
- [ ] **Commit** `feat: driver and owner cancellations with policy-based partial refunds`

### Task 3: Lifecycle job, approval-deadline cap and reminders

**Files:** `booking/BookingJobs` (+ `advanceLifecycle()`, `sendReminders()`), `booking/Booking` (deadline cap), `email/EmailTemplates` (+ reminder templates); tests `booking/LifecycleJobsTest`.

- [ ] **Contract:**
  - Approval deadline when a booking enters `AWAITING_APPROVAL` = `min(now + approvalHours, startTime)`.
  - `advanceLifecycle()` (every 60 s): (a) `CONFIRMED` with `start ≤ now < end` → `ACTIVE` (event SYSTEM "Parking time started"); (b) `CONFIRMED`/`ACTIVE` with `end ≤ now` → `COMPLETED`, `completedAt = now`, earning `HELD → PENDING_PAYOUT` (only from HELD), event, driver notification `BOOKING_COMPLETED` ("Thanks for parking with ParkEase"); (c) `AWAITING_APPROVAL` with `start ≤ now` → handled by the existing auto-reject (deadline ≤ start guarantees it) — add a guard so the reject reason is "The booking start time passed before the owner responded" when `deadline == start`. Each booking processed in its own transaction under payment → booking locks with status re-check. Batches of ≤ 500, ordered by start/end.
  - `sendReminders()` (every 60 s): CONFIRMED with `now < start ≤ now + 60 min` and `reminder_sent_at IS NULL` → driver `BOOKING_STARTING_SOON` notification + email "Your parking starts soon – ParkEase" (IST time, address, slot, booking code), set `reminder_sent_at`; AWAITING_APPROVAL with `now < approvalDeadline ≤ now + 30 min` and `approval_nudge_sent_at IS NULL` → owner `OWNER_APPROVAL_REMINDER` notification + email "Respond to a booking request – ParkEase", set `approval_nudge_sent_at`. Exactly once each (set the column in the same transaction as the notification).
- [ ] **Tests** (fixed/mutable test clock): confirmed booking before start untouched; at start → ACTIVE; at end → COMPLETED with earning PENDING_PAYOUT and notification; confirmed whose whole window passed while the job was down → COMPLETED directly; cancelled/rejected untouched; approval deadline capped at start for a booking starting in 30 min; reminder sent once (run twice); not sent for bookings starting in 2 h; nudge sent once at 25 min before deadline.
- [ ] **Commit** `feat: booking lifecycle transitions, approval cap and reminders`
